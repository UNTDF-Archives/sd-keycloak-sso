| **6.1. `Guia-Teoria.md`: OAuth 2.1 e Implicit Grant** | **OK** | El borrador de OAuth 2.1 (*draft-ietf-oauth-v2-1*, sec. 4.1.2) elimina explícitamente y prohíbe el flujo `Implicit Grant` (`response_type=token`) y `Resource Owner Password Credentials`. La afirmación es correcta. |
| **6.2. `Guia-Teoria.md`: Alcance de PKCE** | **CORREGIR** | `Guia-Teoria.md` (líneas 94 y 428) afirma que PKCE se diseñó únicamente para clientes públicos. Si bien nació para clientes móviles/SPAs (RFC 7636), en la especificación moderna OAuth 2.1 PKCE es **obligatorio para todos los clientes** que usen Authorization Code (tanto públicos como confidenciales). |
| **6.3. `Guia-Teoria.md`: Validación de firmas RS256/HS256 en diagrama** | **CORREGIR** | En el diagrama Mermaid (línea 202) se indica: `DecryptSig[Descifrar Firma con Clave Pública obtenida de JWKS]` y luego una comparación. En criptografía de firmas digitales (RSA / ECDSA), una firma digital **NO se descifra**; se **verifica** mediante el algoritmo de verificación de firma (`RSASSA-PKCS1-v1_5-VERIFY` / `RSASSA-PSS-VERIFY` o ECDSA `Verify`). Usar "descifrar" proviene de la analogía didáctica errónea ("textbook RSA") y es técnicamente incorrecto en estándares como RFC 7515 (JWS). |
| **6.4. `Guia-Teoria.md`: Endpoint de JWKS** | **CORREGIR** | La sección 2.4 (línea 212) titula `Endpoint /.well-known/jwks.json`. En Keycloak no existe un endpoint en esa ruta raíz; la URL real de JWKS es `/realms/{realm-name}/protocol/openid-connect/certs`, la cual se descubre a través del parámetro `jwks_uri` de `/.well-known/openid-configuration`. |
| **6.5. `Guia-Teoria.md`: Claims de JWT** | **OK** | La descripción de claims estándar (`iss`, `sub`, `aud`, `exp`, `iat`) y privados/roles es técnicamente precisa y se ajusta a RFC 7519. |
| **6.6. `Guia-Teoria.md`: 'Bearer-only' en Keycloak moderno** | **CORREGIR** | En las líneas 313 y 333 se define `Bearer-only` como un tipo de cliente activo en Keycloak. En Keycloak moderno (desde la eliminación de los adapters legados y el nuevo Admin Console en v19-v26), la opción y concepto de cliente `Bearer-only` fue **eliminado**. Actualmente un cliente es simplemente confidencial o público (`Client authentication: ON/OFF`), y si es una API backend que solo valida tokens localmente, no habilita flujos interactivos o ni siquiera se registra en Keycloak. |
| **6.7. `Guia-Teoria.md`: Precios y MAU de Auth0** | **OK** | En la línea 365 se menciona que Auth0 factura por MAU (*Monthly Active Users*) y escala de costo a partir del plan gratuito (7.500 MAU para B2C). Esto coincide con el modelo comercial oficial de Auth0 / Okta. |
| **6.8. `Guia-Teoria.md`: Stack de Authentik ('escrito en Python y Go')** | **OK** (con matiz) | El backend central de Authentik está desarrollado en Python (Django) con interfaz en TypeScript/Lit, mientras que sus outposts y proxies satélite fueron desarrollados en Go (con componentes recientes en Rust). La afirmación es válida a nivel general de arquitectura. |
| **6.9. `Guia-Teoria.md`: Endpoint de Discovery y RFC 8414** | **CORREGIR** | En la línea 339 se afirma: *"Keycloak implementa el estándar RFC 8414. Toda la configuración del servidor se consulta dinámicamente en: .../.well-known/openid-configuration"*. El endpoint `/.well-known/openid-configuration` está especificado por **OpenID Connect Discovery 1.0**, no por RFC 8414. La **RFC 8414** estandariza *OAuth 2.0 Authorization Server Metadata* en el endpoint `/.well-known/oauth-authorization-server`. Keycloak implementa ambos, pero la URL citada pertenece a OIDC Discovery. |
